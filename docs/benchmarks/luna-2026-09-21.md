There are 30 supported AEAT pages, one eligible TGSS example, and 11 controls that require review. Errors stay in denominators. **Luna's confidence values are self-reported, not equivalent to Jev confidence.** Acceptance under the same numerical 0.95 policy is descriptive and is not a calibrated equal-risk comparison. Valid-output identity is the primary model comparison. Invalid replies are counted as failures; their potentially correct unvalidated guesses are not salvaged. This therefore measures recognition through the shared output contract, not each model’s maximum classification ability. Both models use our catalog and routing code, so this measures backend substitution rather than an unconfigured chatbot versus the full product.

## Completed review and interpretation

**There is no single winner across these measures.** Jev with context recognizes all 30 supported AEAT model/type pairs and has no wrong acceptance. Luna with context correctly accepts 27/31 eligible pages versus Jev's 20/31, but also wrongly accepts one required-review control. Luna image-only correctly accepts 25/31, has no wrong acceptance, and has the highest complete-identity count in this run (37/42). Each condition still has errors or unresolved identities.

Codex, the AI assistant and implementation author, checked **all 210 outcomes** against the unchanged visual references. [Completed per-page findings and corrections](luna-2026-09-21-review.json). This is not independent human annotation.

- **The material false acceptance is Facturae p18.** It is an introduction to “Ejemplo 2” and an explanation of the CABECERA block, with illustrative values. Luna text instead returns `invoice`, with kind confidence/probability **0.99/0.99**, and accepts it. The contextual path preserves an already accepted isolated decision, so it does not retry this mistake. I reopened the source image and confirmed the existing `instructions / not_applicable / none` reference. Jev fails response validation on the same page; that is not a successful review either. Luna vision correctly identifies it as guidance and holds it.
- **Luna's extra correct contextual routes** include 036 p15/p18, the 111 bank copy, 202 p2/p3/p4, 347 p6 and 369 p14. It loses 036 p8 to an output-validation failure, producing a net gain of seven correct eligible acceptances. This is higher observed coverage, not equal-risk calibration.
- **Unsupported models remain important:** Luna correctly chooses `none` on 117 and 124. Jev guesses 123 for the 124 page but holds it; its 117 contextual response fails. The 347 continuation still needs neighboring evidence and remains held; Luna's contextual authority stays `unknown`.
- **Illustrated guidance exposes different weaknesses:** Jev calls ATC instruction p15/p16 tax forms, although regional scope keeps review. Luna vision correctly recognizes all four selected ATC instruction pages; Luna text has validation failures on p2/p15. Facturae guide pages also cause authority uncertainty in several Luna conditions.
- **There are nine unique failed backend requests:** four Jev text, four Luna text, one Luna image. Reused failed isolated outcomes also appear in contextual denominators. Luna's failed calls reached a completed CLI reply with usage recorded, then failed JSON/response validation; exact unvalidated guesses were not retained for scoring. The four Jev failures have unknown token usage. No failed response was repaired or replaced.

**What this means for the project:** this run supports keeping the shared OCR, catalog, routing policy, CLI contract and audit records. It does not justify claiming Jev outperforms a general-purpose LLM, or replacing Jev with Luna under unchanged confidence assumptions. The 0.99 false acceptance is direct evidence that Luna's self-reported confidence is not a safety guarantee. A separately calibrated text/vision fallback is a candidate for a new evaluation, not a tested production feature here.

The completed, separately frozen **[label-only follow-up](luna-labels-2026-09-21.md)** removes the probability-distribution requirement. It produces valid replies for all 42 pages but only **31/42 complete identities** and **28/30 AEAT model/type pairs**, and still mistakes Facturae p18 for an invoice. There are no confidence or acceptance claims for that condition. It is explicitly post-hoc and cannot repair or replace these original outcomes; see the [follow-up protocol](../../eval/LUNA-BENCHMARK.md#separate-follow-up-labels-without-probability-distributions).

## Controls and limits

- All 237 source-page OCR fingerprints and all 42 image hashes were verified before inference. The image-only condition supplies 300-DPI full-page PNGs with opaque filenames and no OCR text. Codex may resize images internally. 57 text requests made by both providers have identical evidence-and-question hashes; conditional context retries can differ by model.
- Every Luna call is a fresh ephemeral session, requested as `gpt-5.6-luna` with low reasoning effort. Tools, browsing, memories and project instructions are disabled, and any observed tool activity invalidates the outcome. Codex system/skill-description overhead remains. This is Luna through the signed-in Codex CLI, not a bare API call or a reused judge conversation. The explicit requested model is recorded; CLI events do not provide a separate resolved-model snapshot identifier.
- Fresh Jev runs use `jev-1.13.0`. Each context condition reuses its model's isolated reply before the existing optional retry. Original outputs, provider errors and wrong acceptances are preserved. No threshold fitting, repaired predictions or best-of reruns are applied.
- These public templates have already informed our OCR and Jev-oriented Choice prompts. Both original partitions are development data. Pages within PDFs are correlated. This does not establish production, field/amount extraction, PGC, broad scan-quality or adversarial robustness performance. The image-only column changes evidence representation as well as workflow; it is not an isolated model substitution.
